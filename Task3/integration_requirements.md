# Требования к интеграции с партнёром «Умный дом»

## 1. Объём интеграции

PropDevelopment интегрируется с одной партнёрской платформой, которая предоставляет два сервиса:

- **Интеллектуальный домофон**: видеозвонок собственнику + биометрический доступ по лицу
- **Интеллектуальный шлагбаум**: распознавание автомобильных номеров с автоматическим открытием

Доступ к новым функциям — через существующее мобильное приложение собственника. Новые контейнеры в ландшафте PropDevelopment не должны нарушать существующие домены и интеграции.

## 2. Архитектурные решения

### 2.1 Где хранится биометрия — ключевое решение

**Решение**: биометрические шаблоны (лицо) и шаблоны автомобильных номеров **хранятся на стороне партнёра**, не в PropDevelopment.

**Обоснование**:

- Биометрия — специальная категория ПДн по **ст. 11 ФЗ-152** («биометрические персональные данные»). Хранение и обработка требуют отдельной инфраструктуры compliance, на которую PropDevelopment не специализируется.
- Партнёр как провайдер услуги несёт основную ответственность за хранение шаблонов. PropDevelopment выступает оператором, который заключает с партнёром DPA (data processing agreement).
- В системах PropDevelopment остаётся только **handle/идентификатор** биометрической записи на стороне партнёра + метаданные привязки (к какой квартире/собственнику он относится, статус согласия, дата отзыва).

**Что хранится в `iot-integration-db`** (новая БД на стороне PropDevelopment):

- Маппинг `apartment_id ↔ partner_device_id` (домофоны, шлагбаумы по ЖК)
- Маппинг `tenant_id ↔ partner_biometry_handle` (без самих биометрических данных)
- Журнал согласий собственников на обработку биометрии и номеров ТС
- Audit trail всех действий с устройствами (open, deny, enroll, revoke)

### 2.2 Новый сервис `iot-integration-app`

Появляется отдельный контейнер на стороне PropDevelopment:

- Принимает синхронные запросы от `tenant-core-app` (REST/HTTPS)
- Транслирует команды в API партнёра через Partner API Gateway
- Принимает webhooks от партнёра (звонок в домофон, событие распознавания) и формирует push-уведомления в мобильное приложение
- Изолирует партнёрские учётные данные (mTLS-сертификаты, токены) от остальных систем PropDevelopment
- Реализует circuit breaker — при отказе партнёра не блокирует основные сценарии `tenant-core-app`


### 2.3 Партнёрский API Gateway

Весь трафик в обе стороны проходит через API Gateway на периметре PropDevelopment:

- **Входящие webhooks**: проверка mTLS, IP allow-list партнёра, rate-limiting, валидация подписи запроса
- **Исходящие вызовы**: проксирование клиентских сертификатов, единая точка ротации credential, единый аудит
- Тот же API Gateway может использоваться и для интеграций с УК (см. Task2, дополнительный пункт I.15) — это снимает несколько проблем разом

## 3. Требования к безопасности

### 3.1 Конфиденциальность

- **TLS 1.3** на всех каналах; версии ниже отклонять на уровне gateway
- Шифрование `iot-integration-db` (хранятся handles ПДн собственников и журнал согласий)
- **Видеопоток домофона**: end-to-end шифрование от устройства до мобильного приложения, backend PropDevelopment **не имеет ключей** для расшифровки видео

### 3.2 Целостность

- Все запросы к партнёру и от партнёра подписываются **HMAC-SHA256** с использованием общего секрета + timestamp + nonce
- Audit-журнал `iot-integration-app` хранится в режиме read-only после записи на глубину 1 год
  
### 3.3 Доступность

- SLA партнёра: **≥ 99,9%** (домофон должен работать с высокой доступностью)
- **Fallback на локальное открытие** (физический ключ + PIN на устройстве) при недоступности облака партнёра
- Circuit breaker в `iot-integration-app`: при отказе партнёра возвращаем ошибку 503 без блокировки `tenant-core-app`

### 3.4 Защита биометрических ПДн

- Явное **отдельное согласие** собственника на обработку биометрических ПДн (ст. 11 ФЗ-152) — собирается в мобильном приложении до первого enrollment
- Возможность отзыва согласия в любой момент → удаление шаблона на стороне партнёра по API + удаление handle в `iot-integration-db` в течение **30 дней** с момента запроса

### 3.5 Защита автомобильных номеров

- Номер ТС — косвенно идентифицирующие ПДн (ФЗ-152 в части идентификации субъекта)
- Согласие собственника — обязательно (отдельный пункт от биометрии)
- Шаблон номера хранит партнёр; PropDevelopment видит только **маскированный** номер (`A***777*77`) для UI журнала событий

### 3.6 Tenant isolation

- Партнёр работает только с устройствами, привязанными к ЖК PropDevelopment; не должен иметь возможности обратиться к произвольному API
- Каждый webhook от партнёра проверяется на принадлежность устройства к ЖК PropDevelopment по `device_id` → `apartment_id` в `iot-integration-db`. Если устройство не привязано — событие отклоняется и алертится

## 4. Аутентификация и авторизация

### 4.1 PropDevelopment → Партнёр (исходящие вызовы)

- **Аутентификация транспорта**: mTLS — серверный сертификат партнёра проверяется по pinned CA, клиентский сертификат PropDevelopment предъявляется при каждом соединении
- **Авторизация на API**: OAuth 2.0 client credentials grant с access token. Scopes:
  - `intercom:command` — управление домофоном
  - `barrier:command` — управление шлагбаумом
  - `biometry:enroll` — регистрация лица
  - `biometry:revoke` — удаление шаблона
  - `vehicle:enroll` / `vehicle:revoke` — то же для автономеров
- **Ротация**: client cert — каждые 90 дней (автоматически через cert-manager); access token TTL 1 час; refresh — стандартный

### 4.2 Партнёр → PropDevelopment (входящие webhooks)

- **Аутентификация**: mTLS (партнёр предъявляет свой client cert; gateway проверяет CA и Subject)
- **Подпись запроса**: header `X-Partner-Signature: hex(HMAC_SHA256(secret, timestamp || nonce || body))`
- **Replay-защита**: проверка `timestamp` (отклонять при отклонении ≥ 5 минут от текущего времени); проверка `nonce` (хранится 10 минут в Redis, повтор отклоняется)
- **Авторизация на gateway**: IP allow-list партнёра (отсекает чужие IP до криптопроверок) + фильтр по списку допустимых типов событий из контракта; неизвестные типы отклоняются
- **Авторизация события**: tenant isolation на стороне `iot-integration-app` — `device_id` из webhook должен быть привязан к одному из ЖК PropDevelopment в `iot-integration-db`, иначе событие отклоняется и алертится (см. 3.6)


## 5. Взаимодействие систем

### 5.1 Сценарии и потоки

| № | Сценарий | Поток данных |
|---|---|---|
| 1 | Звонок в домофон | Устройство → облако партнёра → webhook → API Gateway → `iot-integration-app` → push (FCM/APNs) → мобильное приложение |
| 2 | Ручное открытие домофона из приложения | Мобильное → `tenant-core-app` → `iot-integration-app` → API Gateway → Партнёр → Устройство |
| 3 | Регистрация лица | Мобильное (фото) → `tenant-core-app` → `iot-integration-app` → API Gateway → Партнёр (вычисляет шаблон, возвращает handle) → handle в `iot-integration-db` |
| 4 | Распознавание лица на домофоне | Локально на устройстве/в облаке партнёра, **без участия PropDevelopment**; событие открытия отправляется webhook'ом для журнала |
| 5 | Регистрация автомобильного номера | Мобильное (номер) → `tenant-core-app` → `iot-integration-app` → Партнёр → handle → `iot-integration-db` |
| 6 | Распознавание номера на шлагбауме | Локально на устройстве/в облаке партнёра; webhook о результате |
| 7 | Журнал событий собственника | Все webhook от партнёра → `iot-integration-app` → запись в `iot-integration-db` → доступ через `tenant-core-app` для своих устройств |
| 8 | Отзыв согласия / удаление | Мобильное → `tenant-core-app` → `iot-integration-app` → API партнёра (revoke) → удаление handle |

### 5.2 Протоколы

| Канал | Протокол | Стиль | Аутентификация |
|---|---|---|---|
| Мобильное приложение ↔ `tenant-core-app` | HTTPS / REST | sync | OIDC через `auth-service-1` |
| `tenant-core-app` ↔ `iot-integration-app` | HTTPS / REST | sync | Internal mTLS + service token |
| `iot-integration-app` → API Gateway → Партнёр | HTTPS / REST | sync | mTLS + OAuth 2.0 |
| Партнёр → API Gateway → `iot-integration-app` | HTTPS Webhook | async | mTLS + HMAC-подпись |
| Push-уведомления собственникам | FCM / APNs | async | provider token |
| Видеопоток домофона | WebRTC через инфраструктуру партнёра | streaming | E2E (PropDevelopment не proxy) |
